# HR workflow audit and verification backlog

This is an initial evidence inventory, not a declaration that the whole HR product is complete. Operational registers and drawer recovery were released in PRs #423 and #424. The next audit covers document management, lifecycle execution and HR administration, with restricted-case and reminder operations tracked separately. Source inspection and fixture tests cannot certify every authenticated browser-to-database workflow.

## Administration recovery bundle

Teams previously retained `canManage` after a failed People/context read, and a network exception could leave either administration page loading indefinitely. Teams and Administrators now clear loaded rows, selections/confirmation state and management permission before reading. Read failures are generic, old response bodies are not echoed, strict Boolean permission/candidate flags are required, requests use client no-store caching and abort cleanup, and each page has Refresh. Teams commits its team list and People/context list together only after both reads succeed. An open Team draft is preserved, but its submit button and handler require current management permission. Every real write remains subject to the existing API authorization.

The existing create/edit/archive/restore/grant/revoke endpoints and write payloads are unchanged. Rejected network requests and server errors on create/edit/archive/restore/grant/revoke now produce an explicit unknown-outcome state, clear stale management controls and require a fresh read before another action. Grant/Save leave their busy state. Team drafts remain visible but locked until the form is closed and current Teams are checked; a refresh alone cannot resubmit the same uncertain draft. Reads already pending when the write becomes uncertain cannot restore controls. No write is automatically retried. This UI recovery proof does not establish whether a failed real request committed in the database.

## Validation limits

The lifecycle verification used `scripts/tests/verify-hr-lifecycle-task-completion.sh` at application commit `d1a27ec9cd98bfc3e537c8e72889e67a6ea54b23`. It created its own loopback-only Postgres container, applied the existing lifecycle SQL to that disposable database, ran three completion tests, eleven task-action/approval tests and six workflow tests, and removed the container. No hosted database, production migration or live HR record was involved. Two additional workflow tests reject audit inserts through a disposable CHECK constraint, assert SQL error 23514, and prove start leaves no workflow/tasks/audit behind and cancellation preserves full workflow/task/audit snapshots. Both operations recover after the constraint is removed. Six further cases compare full workflow/task/approval/audit snapshots after rejected task or approval audit inserts, then demonstrate recovery after removing the constraint. These include failure of the workflow-completion audit after a final approval. Expanded tests exposed and corrected fixture cleanup that previously left approval audit rows between cases; the full disposable suite passed after that correction. These proofs cover the tested mutation service paths, not authenticated HTTP/browser routing or every infrastructure failure.

The administration browser flows execute the real pages with synthetic HTTP responses and use synthetic responses; six additional flows abort exactly one attempted write and then prove Refresh uses reads without repeating that write. The Teams flows use the real drawer. They cover loaded management controls, denied refresh, old-row/control clearing, generic messages and successful refresh recovery. Component checks additionally cover malformed flags, People/context-only failure, abort/unmount/late responses, cleared explicit grant selection and preserved-but-disabled Team drafts. Eight additional component cases cover all six writes, server errors, preserved locked drafts and pending-read races. Existing static assertions were updated to recognize abort options and strict Boolean flags without weakening endpoint/authority requirements.

Prior broader HR tests and new focused checks do not replace the outstanding authenticated mutation proof above. This audit remains ongoing. New code requires exact-head PR checks and separate release approval; approvals for #423/#424 do not authorize this follow-up's automatic production deployment.


## Administration route proof limits

The administration suite runs through the existing disposable harness (scripts/tests/verify-hr-lifecycle-task-completion.sh) after the 20 lifecycle tests. Its 20 tests invoke real Next route handlers, real HR context/validation helpers and real audit SQL through a pg-backed driver seam. Login/session and People module enablement are controlled fixtures. The fixture adds the administration columns and Teams table needed by these routes to the local lifecycle scaffold; it is not a certification of the complete production schema or its migrations. No hosted database is used. The first run exposed a missing created_by column in that scaffold; after correction, the full 40-test harness passed and its container was removed. A request paused before context resolution proves the current database grant is re-read, but does not prove cancellation of an action revoked after its authorization check. Administration audit logging remains the existing best-effort ADR policy; this proof does not substitute lifecycle atomic-audit semantics for it.


## Document database proof limits

The expanded disposable harness now passes 48 tests: 20 lifecycle, 20 administration routes and eight employee-document mutation tests. The document suite applies the existing HR document and assurance SQL to the disposable lifecycle fixture, invokes real mutation services and executes their transactions/advisory locks/CTEs through a pg-backed driver. Storage is a separate in-memory map; it uses synthetic text bytes and proves cleanup of an uploaded fixture object after denied or rolled-back version changes. It never creates a live Blob store, uses storage credentials or sends email. It proves one current version after competing uploads, one acknowledgement under concurrent requests, repeat verification history, preservation of immutable versions on logical deletion and tested audit rollback paths. These are service/database checks, not authenticated HTTP/browser upload/download proof, real storage durability or every race/failure combination. The independent schema harnesses passed all 30 document checks and 33 assurance checks; those include schema-only reminder-ledger constraints, not delivery operations. All disposable containers were removed.
